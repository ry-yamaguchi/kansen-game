# 開発の掟

個人開発（Ryosuke / meryo）の横断ノウハウから、このプロジェクトに効くものを抜いたものである。

## 1. 推測で実装しない

外部ライブラリや API の挙動は、公式ドキュメントと実測で判断する。思い出しで書かない。

## 2. 面白さの検証を、絵より先に置く

**仕様を満たしても遊べなければ失敗である。** 描画を作り込む前に、ヘッドレスで
シミュレーションだけを何十回も回し、勝敗が割れるか・「静かに広げてから牙を剥く」戦略が
数字の上で効くかを確かめる。ここが成立しないうちは絵に時間を使わない。

## 3. 確認を頼むときは、コマンドを添える

作者（人間）に動作確認を頼むときは、古いプロセスを止めてから起動するところまでを
1つのコマンドにまとめて渡す。起動しっぱなしの古いサーバが応答して、直っていないものを
「直った」と判定する事故を防ぐ。

## 4. 文体

| 対象                                   | 文体           |
| -------------------------------------- | -------------- |
| コードのコメント、設計文書、コミットメッセージ | 「である」調   |
| **画面に出る文言、エラーメッセージ**   | **「です・ます」調** |

画面の文言は、遊ぶ人が読むものである。失敗を伝えるときは原因と次にとれる行動を添える。

## 5. コミット

- author は `meryo <meryo2000@gmail.com>`（このリポジトリの git config に設定済み。
  グローバル設定は仕事用なので上書きしないこと）。
- `Co-Authored-By` 行は付けない。
- コミット履歴は書き換えない（rebase・force push をしない）。
- commit の前に `git status --short` で、自分が意図していないファイルが混ざっていないか目で見る。

## 6. 秘密情報

キー・トークンをコミットしない。`.env` を追跡しない。このリポジトリは**公開**である。
